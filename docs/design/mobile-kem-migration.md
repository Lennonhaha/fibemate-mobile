# Mobile ML-KEM migration: dual engine, mandatory re-key, sunset 2027-Q1

Status: **design only** — no production code changed. Drafted 2026-10-28.
Tracking issue: `Lennonhaha/fibemate-mobile#94`. Evidence: sandbox runs described below and in the issue comments.

---

## 1. What we measured

The current mobile engine (`src/crypto/ml-kem-768.js`) is used for identity key generation only (`src/services/keyService.ts:49`); there are no production `encapsulate` / `decapsulate` call sites in this repository yet.

Sandbox comparison against the FIPS 203 implementation in `fibemate/packages/pqc-kem/src/ml-kem-768.js` and `@noble/post-quantum@0.7.1`, fixed `d`, `z`, `m`:

| Check | Result |
|---|---|
| Legacy ct → legacy decaps | works (`ss = SHA3-256(K̄ ‖ H(c))`, `K̄ = SHA3-256(m‖H(pk))`) |
| Legacy ct → FIPS decaps | **implicit rejection**: returns `J(z‖c) = SHAKE256(z‖ct, 32)` |
| FIPS ct → legacy decaps | **implicit rejection**: returns `SHA3-256(z‖H(c))` |
| FIPS ct → FIPS decaps with a **legacy keypair** | **implicit rejection** |
| FIPS impl vs noble, 3 fixed seeds | byte-identical `pk`/`sk`/`ct`/`ss`, both directions |

Two independent defects, not one:

1. **Encryption sampling.** Legacy `encapsulate` samples the noise polynomials from `m` directly (`shake256([...m, i])`). FIPS 203 derives 32 bytes `ρ = G(m ‖ H(ek))[32:64]` and samples from `ρ`. Same `m` and `pk` therefore produce different ciphertexts, and both sides fail the re-encryption check inside decapsulation.
2. **Domain of the key material.** Legacy key generation works in the **time domain** and encodes `t = A·s + e` and `s` directly. FIPS 203 requires the NTT-domain encodings `t̂` and `ŝ`. A legacy `pk` is not a valid ML-KEM-768 encapsulation key, and a legacy `sk` cannot decapsulate a FIPS ciphertext.

Additional deviations: `G(d)` omits the parameter-set byte `k`; `G` is SHA3-256 instead of SHA3-512; the final secret adds a Kyber-round-3-shaped `SHA3-256(K̄‖H(c))` step. The module is neither FIPS 203 nor Kyber round 3.

## 2. Consequences that drive the design

- **A KDF adapter cannot work.** Rejection occurs before any KDF is applied.
- **Identity rotation is mandatory.** Keys generated by current builds are not FIPS 203 keys; no engine change can make them consumable by a correct peer.
- **Any FIPS peer that encapsulates to a currently published mobile `pk` fails silently.** The peer derives a secret nobody can open; no error surfaces. This is the B-side POC failure mode.
- **The "FIPS 203" label is currently false**, not merely stale: `KeysScreen.tsx:110-111`, `keyService.ts:3`, `README.md:15`.

## 3. Goals / non-goals

Goals

1. New identities and all new sessions use a FIPS 203 engine.
2. Existing users are re-keyed without losing access to data they can still decrypt.
3. Peers still running the legacy variant can interoperate during a bounded window, with no silent failures.
4. The false claim disappears in the same change that introduces the new engine.

Non-goals

- No change to SM2/SM3/SM4 or to the ratchet-store work tracked separately (`storage.ts` policy notes that a session-blob API is not part of this module).
- No attempt to salvage legacy ciphertexts by re-deriving keys.
- No automatic fallback that tries both engines on decrypt failure (see §5).

## 4. Target architecture

```
src/crypto/kem/
  index.ts          // KemEngine interface + engine registry
  fips.ts           // new: wraps packages/pqc-kem equivalent (or a vendored copy)
  legacy.ts         // current ml-kem-768.js, renamed, unexported from public index
```

```ts
export type KemVersion = 'v1_legacy' | 'v2_fips';

export interface KemEngine {
  readonly version: KemVersion;
  generateKeypair(): { publicKey: Uint8Array; secretKey: Uint8Array };
  encapsulate(peerPublicKey: Uint8Array): { ciphertext: Uint8Array; sharedSecret: Uint8Array };
  decapsulate(secretKey: Uint8Array, ciphertext: Uint8Array): Uint8Array;
}
```

Rules

- `crypto/index.ts` exports **only** the FIPS engine and the `KemVersion` type. The legacy engine is reachable through an explicit internal path used solely by the legacy decapsulation branch.
- Engine selection is by **declared version**, never by trial decryption: `identity.kem_version` for our own key, peer capability tag for theirs.
- Engine objects are stateless; randomness comes from `expo-crypto` (`globalThis.crypto.getRandomValues` already polyfilled in `crypto/index.ts`).

## 5. Versioning and negotiation

### 5.1 Data model

```ts
export type IdentityMaterial = {
  kem: {
    version: KemVersion;
    publicKey: string;   // base64url
    privateKey: string;  // base64url
  };
  sm2: { publicKey: string; privateKey: string };
  createdAt: string;
};
```

- `version` is mandatory on write; absent = `v1_legacy` on read (that is what shipped builds wrote).
- Session/ratchet state, when it lands, carries the same field. A session's `kem_version` is the negotiated value, not our identity's version.

### 5.2 Negotiation

1. Registration and pre-key publication include `kem_version` alongside the public key. The server stores and returns it; a missing field means `v1_legacy`.
2. Initiator chooses the engine from the responder's advertised version (highest mutually supported). New clients always advertise `v2_fips`.
3. Responder decapsulates with the engine named by the ciphertext's tag. A `v2_fips` ciphertext is never offered to the legacy engine and vice versa.
4. **No blind dual-try.** Never attempt both engines and accept whichever returns a key: that turns the migration into a downgrade oracle, and in our case both engines return a well-formed 32-byte value, so there is nothing to distinguish.

### 5.3 Failure semantics

- Wrong-version ciphertext must fail with an explicit, typed error (`KemVersionMismatch`), logged with both versions. Today the equivalent failure is a silent wrong key — that is the defect we are removing.
- FIPS decapsulation can still hit implicit rejection for corrupted ciphertexts; that is indistinguishable from a tampered ciphertext by design, so surface it as `DecapsulationFailed` without exposing which check failed.

## 6. Re-keying existing users

Ordered steps on first launch after upgrade:

1. Read `IdentityMaterial`; if `kem.version` is absent or `v1_legacy`, generate a `v2_fips` keypair.
2. Keep the legacy keypair in secure storage under a suffixed key (`..._legacy`) — it is still required to talk to peers on old builds during the window.
3. Publish the new public key and version to the server (and to the pre-key bundle) **before** dropping the legacy advertisement.
4. Show a one-time notice: the security label is being corrected, and contacts on older versions may need to upgrade for new sessions.
5. Never delete the legacy private key before the sunset date; it is the only way to read legacy-era material that is still in flight.

If the server cannot store two public keys for one account, publish only `v2_fips` and accept that old-build peers cannot start new sessions with this account (they still can finish ones already established). That trade-off belongs to the server-side migration plan, not to this module.

## 8. Sunset

- **Date: 2027-03-31 (2027-Q1 end).** On that date the legacy engine is deleted, `v1_legacy` identities stop being accepted, and old-build clients receive an explicit "unsupported key version" error instead of a silent mismatch.
- Preconditions to keep the date: telemetry showing no active `v1_legacy` handshakes for 30 consecutive days, and server support for the version field in place.
- After deletion, `v1_legacy` ciphertexts must fail loudly; no compatibility shim is retained.

## 9. Test plan

Unit / property tests (CI gate, no network):

1. **Cross-version matrix** (3 × 3): `v1→v1` succeeds; `v2→v2` succeeds; `v1→v2` and `v2→v1` raise `KemVersionMismatch` — asserted as an *error*, not merely as "different outputs".
2. **FIPS vs oracle**: `generateKeypair` / `encapsulate` are deterministic under injected randomness and byte-identical to `@noble/post-quantum` on at least 3 fixed seeds (already demonstrated in the sandbox; port the harness).
3. **Legacy key isolation**: a `v1_legacy` `pk` must be rejected by the FIPS engine's public-key validation before encapsulation (it is not a valid `ek`), so the failure is local and explicit rather than remote and silent.
4. **No silent fallback**: a test that fails if any code path calls both engines in the same handshake attempt.
5. **Storage migration**: reading an `IdentityMaterial` without `version` yields `v1_legacy`; the re-key routine is idempotent; the legacy key is preserved under its suffixed slot.

Manual / device:

- Fresh install → identity is `v2_fips`; label shows the real version.
- Upgrade with an existing `v1_legacy` identity → re-key happens, legacy key retained, notice shown.
- Old build ↔ new build → new session blocked with an explicit error, existing session continues.

## 10. Risks

| Risk | Mitigation |
|---|---|
| Server has no version field | Ship the field first; until then the new client advertises `v2_fips` locally and does not start new sessions with peers lacking the tag |
| Users on old builds lose the ability to start sessions | Explicit notice + sunset date; keep legacy decaps during the window |
| Silent failures persist somewhere else (desktop/web) | Same class of defect must be checked in every client that consumes mobile public keys; this document covers mobile only |
| Legacy key deleted by a storage cleanup | Legacy slot uses a separate key name and is excluded from routine cleanup; test 5 covers it |
| Ratchet store (separate work) lands without a version field | Make `kem_version` a required field of the session record before that work merges |

## 11. Open questions

1. Does the registration API currently accept an extra `kem_version` field, or does it need a schema change? (Server repo.)
2. Can one account hold two `mlkem` public keys during the transition, or must we publish only the new one?
3. Do any current users have `v1_legacy` ciphertexts at all? Mobile never encapsulated, but peers may have produced ciphertexts against mobile public keys; this determines whether the legacy decapsulation path is ever exercised in practice.
4. Who consumes the mobile `pk` today (server, desktop, web)? That consumer's engine determines whether the false key is already causing silent failures in the field.

## 12. Acceptance criteria for the implementation PR

- FIPS engine is the only engine reachable from `crypto/index.ts`.
- `kem_version` present on every newly written identity and on the registration payload.
- Re-key path implemented and covered by tests 1, 3, 5.
- All four copy locations corrected; no "FIPS 203" text attached to a `v1_legacy` key.
- Cross-version matrix raises typed errors; no silent mismatch anywhere in the KEM boundary.
- Sunset date documented in code (constant + comment) and in this file.
