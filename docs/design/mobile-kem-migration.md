# Mobile ML-KEM migration: clean break

Status: **design only** — no production code changed. Revised 2026-10-29 (supersedes the dual-engine draft of 2026-10-28).
Tracking issue: `Lennonhaha/fibemate-mobile#94`. Evidence: sandbox runs and the issues comments referenced below.

---

## 1. What we measured

The current mobile engine (`src/crypto/ml-kem-768.js`) is used for identity key generation only (`src/services/keyService.ts:49`); there are no production `encapsulate` / `decapsulate` call sites in this repository.

Sandbox comparison against the FIPS 203 implementation in `fibemate/packages/pqc-kem/src/ml-kem-768.js` and `@noble/post-quantum@0.7.1`, fixed `d`, `z`, `m`:

| Check | Result |
|---|---|
| Legacy ct → legacy decaps | works (`ss = SHA3-256(K̄ ‖ H(c))`, `K̄ = SHA3-256(m‖H(pk))`) |
| Legacy ct → FIPS decaps | **implicit rejection**: returns `J(z‖c) = SHAKE256(z‖ct, 32)` |
| FIPS ct → legacy decaps | **implicit rejection**: returns `SHA3-256(z‖H(c))` |
| FIPS ct → FIPS decaps with a **legacy keypair** | **implicit rejection** |
| FIPS impl vs noble, 3 fixed seeds | byte-identical `pk`/`sk`/`ct`/`ss`, both directions |

Two independent defects, not one:

1. **Encryption sampling.** Legacy `encapsulate` samples the noise polynomials from `m` directly (`shake256([...m, i])`). FIPS 203 derives 32 bytes `ρ = G(m ‖ H(ek))[32:64]` and samples from `ρ`. Same `m` and `pk` therefore produce different ciphertexts.
2. **Domain of the key material.** Legacy key generation works in the **time domain** and encodes `t = A·s + e` and `s` directly. FIPS 203 requires the NTT-domain encodings `t̂` and `ŝ`. A legacy `pk` is not a valid ML-KEM-768 encapsulation key, and a legacy `sk` cannot decapsulate a FIPS ciphertext.

Additional deviations: `G(d)` omits the parameter-set byte `k`; `G` is SHA3-256 instead of SHA3-512; the final secret adds a Kyber-round-3-shaped `SHA3-256(K̄‖H(c))` step. The module is neither FIPS 203 nor Kyber round 3.

## 2. What exists in the field (measured, not assumed)

Checked read-only against production on 2026-10-29:

- `src/services/regClient.ts:101-116` registers **only the SM2 public key** (`identityKey`); the ML-KEM keypair has **no upload path**.
- OPK publication is X25519 (`src/crypto/opk-client.ts:73`), not ML-KEM.
- Production data: 65 user records, **0** containing any `mlkem` / `ml-kem` field. The only ML-KEM material is `hybridBundleHex` on three `isTestUser=1` accounts (1217 B = 33 B compressed SM2 point + 1184 B ML-KEM-768 pk), written by web/desktop clients, whose engines produce structurally valid keys.
- Server endpoints `POST /api/mlkem/register` and `GET /api/mlkem/public-key/:userId` exist but have never been used (0 records).

**Conclusion:** there are no published mobile ML-KEM public keys, therefore no ciphertexts addressed to them, therefore nothing to remain compatible with. A compatibility window would protect a population of zero.

## 3. Consequences that drive the design

- **A KDF adapter cannot work.** Rejection occurs before any KDF is applied.
- **Identity KEM keys must be replaced, not migrated.** Keys generated by current builds are not FIPS 203 keys; no engine change makes them consumable by a correct peer.
- **The "FIPS 203" label is currently false**, not merely stale: `KeysScreen.tsx:110-111`, `keyService.ts:3`, `README.md:15`.
- **The dual-engine design is unnecessary.** It was justified by existing keys and ciphertexts; the measurement in §2 shows both are zero.

## 4. Goals / non-goals

Goals

1. One engine: FIPS 203. No legacy decapsulation path is retained.
2. Existing installs replace their KEM keypair once, automatically and idempotently.
3. Any encounter with legacy KEM material — a stale local key, a peer advertising one, a ciphertext tagged as legacy — fails **explicitly**, never silently.
4. The false claim disappears in the same change that introduces the new engine.

Non-goals

- No change to SM2/SM3/SM4, or to the ratchet-store work tracked separately (`storage.ts`).
- No attempt to salvage legacy ciphertexts by re-deriving keys (there are none, and none can be made to work).
- No dual-try fallback on decrypt failure (see §6).

## 5. Target architecture

```
src/crypto/kem/
  index.ts      // KemEngine interface; exports the FIPS engine only
  fips.ts       // wraps the packages/pqc-kem equivalent (or a vendored copy)
```

```ts
export interface KemEngine {
  generateKeypair(): { publicKey: Uint8Array; secretKey: Uint8Array };
  encapsulate(peerPublicKey: Uint8Array): { ciphertext: Uint8Array; sharedSecret: Uint8Array };
  decapsulate(secretKey: Uint8Array, ciphertext: Uint8Array): Uint8Array;
}
```

Rules

- `crypto/index.ts` exports the FIPS engine and nothing else. `src/crypto/ml-kem-768.js` is deleted, not renamed: a reachable legacy engine is a fallback waiting to happen.
- No engine registry, no version enum, no negotiation. A single implementation cannot be downgraded.
- The engine is stateless; randomness comes from `expo-crypto` (`globalThis.crypto.getRandomValues` is already installed by `crypto/index.ts`).

## 6. Failure semantics (the fallback clause)

Clean break must not become "silent break". The two failure modes the old code allowed are both closed here:

- **Legacy public key presented for encapsulation.** The FIPS engine validates the encapsulation key before use (`validate_public_key` / modulus and encoding checks). A legacy `pk` fails that check **locally and loudly** with `InvalidEncapsulationKeyError`, instead of producing a ciphertext nobody can open. This is why the validation step is part of the engine boundary, not optional.
- **Legacy ciphertext or stored legacy key encountered.** Raise `LegacyKemMaterialError` naming the source (`stored_identity`, `peer_payload`, `session_record`) and the byte length. Never attempt decapsulation, never return a derived key, never fall back.

Rules

- No path may call two implementations in the same handshake attempt. A test enforces this (§8.4).
- Errors are typed and carry a reason code; no `catch` may swallow a KEM failure and continue with an empty or zeroed secret. Any consumer that cannot handle the error must fail the session.
- Diagnostics never include key material; lengths and reason codes only.

**Why this clause survives the clean break:** if the assumption in §2 ever turns out to be wrong — a mobile `pk` did reach a peer, or an old ciphertext exists — the first correct behaviour is a loud failure that names the case, not a compatibility shim added after the fact. A loud failure is what makes the discovery cheap.

## 7. Re-keying existing installs

On first launch after upgrade:

1. Read `IdentityMaterial`. If it carries a KEM keypair, discard it (do not keep a `_legacy` slot — keeping it invites accidental use).
2. Generate a FIPS 203 keypair, write it with the same storage key the old code used, so nothing downstream needs to know a migration happened.
3. Mark `kem_rotated_at` for diagnostics only. No server call is required: the old `pk` was never published, so there is nothing to withdraw.
4. Publish the new public key only through a path that actually carries ML-KEM material (currently none; see §10).

Idempotency: running the routine twice must produce one keypair, not two — the second run reads `kem_rotated_at` and returns.

Data at rest that is unaffected: message history and locally stored session keys are not KEM-derived; they keep decrypting exactly as before.

## 9. Test plan (CI gate, no network)

1. **Oracle equivalence**: `generateKeypair` / `encapsulate` deterministic under injected randomness and byte-identical to `@noble/post-quantum` on at least 3 fixed seeds (harness already exists in the sandbox; port it).
2. **Legacy `pk` is rejected locally**: feed a keypair produced by the old module into `encapsulate`; assert `InvalidEncapsulationKeyError` and assert no ciphertext is returned. Negative case, not a warning.
3. **Legacy material fails loudly**: inject a stored legacy key and a session record marked with the old shape; assert `LegacyKemMaterialError` with the correct `source` value.
4. **No dual engine**: a static/runtime assertion that no code path invokes more than one KEM implementation per handshake; deleting the legacy module must break the build if some path still imports it.
5. **Storage migration**: an `IdentityMaterial` with a legacy keypair is rewritten exactly once; running twice is idempotent; the new key validates.
6. **Deletion is complete**: no import of `ml-kem-768.js` anywhere (ESM `from`, CJS `require`, dynamic `import()`, `<script src>`), and the file is absent from the bundle.

Manual / device:

- Fresh install → identity is FIPS 203; label matches.
- Upgrade with an existing identity → key replaced once, no notice required (nothing was published), history still decrypts.
- Peer sending legacy material → explicit error, no silent mismatch.

## 10. When this design must be re-opened

The clean break rests on three measured facts. If any one changes, stop and reassess before shipping:

| Fact (2026-10-29) | How it could change | Reassessment trigger |
|---|---|---|
| Mobile never publishes a KEM `pk` | someone adds an upload path, or a client republishes `hybridBundleHex` from a mobile build | any mobile-origin `pk` appears on the server → the legacy engine question is back |
| No ciphertexts address a mobile `pk` | a peer encapsulated to a `pk` scraped from a device backup or a test account | any legacy ciphertext found in the field |
| No legacy session state exists | the ratchet store lands before this change and records KEM material | inspect the store schema before merging |

Recorded as of the measurement: 65 users, 0 with ML-KEM fields, 3 test-account bundles from web/desktop.

## 11. Open questions

1. Does the registration/update API need a `kem_version` field at all now? Only if mobile starts publishing KEM material. Decision deferred until §10's first row changes.
2. Which client consumes `hybridBundleHex`? Not needed for this migration, but it is the consumer whose engine decides whether mobile could ever be on the other side of an encapsulation.
3. Should the FIPS module be vendored from `packages/pqc-kem` or re-implemented in `src/crypto/kem/fips.ts`? Vendoring keeps one audited implementation; the decision belongs to the implementation PR.

## 12. Acceptance criteria for the implementation PR

- FIPS engine is the only KEM implementation in the repository; the old module is deleted.
- Identity KEM keypair replaced once on upgrade, idempotently; no `_legacy` copy retained.
- Legacy `pk` and legacy stored material raise typed errors; no silent derived key on any path.
- All four copy locations corrected; no claim predates its engine.
- Tests 1–6 pass, including the negative cases.
- This file's §10 table is re-checked and re-dated in the PR description.
